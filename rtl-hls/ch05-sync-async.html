RTL과 HLS 입문5장
5장

동기와 비동기

리셋, 서로 다른 클럭 사이의 신호, 메타스테이빌리티, 그레이 코드와 비동기 FIFO를 다룹니다.

5.1리셋: 동기와 비동기

지금까지 모든 신호는 클럭 엣지에 맞춰 움직였습니다. 이런 신호를 동기(synchronous) 신호라고 합니다. 반대로 클럭과 상관없이 아무 때나 바뀌는 신호가 비동기(asynchronous) 신호입니다. 버튼, 외부 칩에서 오는 신호, 다른 클럭으로 동작하는 회로의 출력이 모두 비동기입니다.

가장 먼저 만나는 예가 리셋입니다. 리셋을 클럭 엣지에서만 확인하는 방식이 동기 리셋, 리셋이 들어오는 즉시 레지스터를 지우는 방식이 비동기 리셋입니다. 코드에서는 감지 목록(sensitivity list)에 리셋이 들어가는지로 구분합니다.

// 동기 리셋: 엣지에서만 rst를 본다
always @(posedge clk)
  if (rst) q <= 0;
  else     q <= q + 1;

// 비동기 리셋: rst가 올라가는 즉시 동작
always @(posedge clk or posedge rst)
  if (rst) q <= 0;
  else     q <= q + 1;

비동기 리셋은 짧은 펄스도 놓치지 않고, 클럭이 멈춰 있어도 동작한다는 장점이 있습니다. 그런데 리셋을 푸는 순간이 클럭 엣지와 겹치면, 어떤 플립플롭은 이번 엣지부터 동작하고 어떤 것은 다음 엣지부터 동작하는 일이 생깁니다. 그래서 실무에서는 “들어갈 때는 비동기로, 나올 때는 클럭에 맞춰서” 리셋을 거는 리셋 동기화기를 씁니다.

// 비동기로 걸리고, 동기로 풀리는 리셋
always @(posedge clk or negedge arst_n)
  if (!arst_n) begin s1 <= 0; s2 <= 0; end
  else         begin s1 <= 1; s2 <= s1; end
assign rst_n = s2;   // 회로 전체는 이 rst_n을 쓴다

5.2메타스테이빌리티

2장에서 setup/hold를 지켜야 한다고 했습니다. 그런데 비동기 신호는 언제 바뀔지 모르니 이 약속을 지킬 방법이 없습니다. D가 setup/hold 구간 안에서 바뀌면, 플립플롭 출력은 0도 1도 아닌 중간 전압에 한동안 머물다가 결국 어느 한쪽으로 떨어집니다. 언덕 꼭대기에 공을 올려놓은 것과 같습니다. 이 상태를 메타스테이빌리티라고 합니다.

공이 언제 떨어질지는 꼭대기에서 얼마나 가까웠는지에 달렸고, 정확히 꼭대기라면 이론상 영원히 걸립니다. 해결책은 간단합니다. 첫 플립플롭이 결정을 내릴 시간을 한 클럭 통째로 주고, 그 결과를 두 번째 플립플롭이 다시 받는 것입니다. 이것이 2단 동기화기(2-FF synchronizer)입니다.

always @(posedge clk) begin
  q1 <= async_in;   // 메타스테이블이 될 수 있음
  q2 <= q1;         // 한 사이클 동안 결정될 시간을 준 뒤 받음
end
// 회로의 나머지는 q2만 쓴다

동기화기가 실패할 확률은 0이 아니라 아주 작을 뿐입니다. 그래서 “평균 몇 년에 한 번 실패하는가”, 즉 MTBF(Mean Time Between Failures)로 따집니다.

MTBF = etr/τ / (T0 · fclk · fdata)　(tr: 결정에 쓸 수 있는 시간, τ, T0: 공정 상수)

tr가 지수에 들어 있다는 점이 핵심입니다. 플립플롭을 한 단 더 두어 tr에 한 클럭 주기가 더해지면 MTBF는 몇 배가 아니라 수십 자릿수가 늘어납니다.

여러 비트짜리 값은 이렇게 넘기면 안 된다 8비트 카운터 값을 비트마다 2단 동기화기로 넘기면, 0111→1000처럼 여러 비트가 동시에 바뀔 때 비트마다 다른 사이클에 넘어가서 엉뚱한 값(예: 1111)을 잠깐 보게 됩니다. 여러 비트는 한 번에 한 비트만 바뀌는 그레이 코드나, 아래의 비동기 FIFO로 넘깁니다.

5.3여러 비트를 넘기는 법: 그레이 코드

위 주의 문단을 직접 확인해 보겠습니다. 클럭 A로 도는 4비트 카운터 값을 클럭 B 쪽에서 비트마다 동기화기로 받습니다. 칩 안에서 비트마다 배선 길이가 조금씩 달라서, 네 비트가 B 쪽에 도착하는 시각도 조금씩 어긋납니다.

그레이 코드는 이웃한 두 수가 항상 한 비트만 다르도록 만든 부호입니다(0000, 0001, 0011, 0010, 0110, …). 한 번에 한 비트만 바뀌므로, B가 바뀌는 순간에 걸려도 옛 값 아니면 새 값 둘 중 하나만 읽습니다.

assign gray = bin ^ (bin >> 1);   // 이진수 → 그레이 코드

비동기 FIFO

클럭이 다른 두 회로가 데이터를 많이 주고받을 때는 비동기 FIFO를 씁니다. 실무에서 클럭 경계를 넘는 데이터 대부분이 이 구조를 거칩니다.

  • 쓰는 쪽은 클럭 A로 메모리에 쓰고 쓰기 포인터를 늘립니다. 읽는 쪽은 클럭 B로 읽고 읽기 포인터를 늘립니다.
  • FIFO가 비었는지 알려면 B 쪽이 쓰기 포인터를, 찼는지 알려면 A 쪽이 읽기 포인터를 알아야 합니다. 클럭 경계를 넘는 것은 이 두 포인터뿐입니다.
  • 포인터는 1씩 늘어나는 카운터이므로, 그레이 코드로 바꾼 뒤 2단 동기화기로 넘깁니다. 위 실험과 똑같습니다.

데이터 자체는 메모리에 머물러 있다가 포인터가 넘어간 뒤에 읽히므로 동기화기가 필요 없습니다. 넘겨받은 포인터가 한두 사이클 늦을 수는 있지만, 그 결과는 “아직 비었다고 본다” 또는 “아직 찼다고 본다”처럼 항상 안전한 쪽으로만 틀립니다.

포인터에는 칸 수보다 한 비트를 더 둡니다. 4칸 FIFO라면 포인터가 3비트이고, 아래 두 비트는 칸 번호, 맨 위 비트는 “몇 바퀴째인가”입니다. 두 포인터가 완전히 같으면 비었고, 칸 번호는 같은데 맨 위 비트만 다르면 쓰는 쪽이 한 바퀴 앞서 있다는 뜻이므로 꽉 찬 것입니다.

실제 비동기 FIFO에서는 이 비교를 그레이 코드로 넘겨받은 포인터로 합니다. 넘겨받은 포인터는 2단 동기화기 때문에 몇 사이클 늦으므로, 쓰는 쪽은 실제보다 “더 찼다”고, 읽는 쪽은 “더 비었다”고 봅니다. 둘 다 안전한 쪽입니다.

5.4짧은 펄스 넘기기

빠른 클럭 A에서 한 사이클짜리 펄스(“이벤트가 한 번 일어났다”)를 느린 클럭 B로 넘긴다고 해 봅시다. 2단 동기화기를 그대로 달면, 펄스가 B의 엣지 사이에서 시작해서 끝나 버려 B가 아예 보지 못할 수 있습니다. 5.1의 동기 리셋이 짧은 펄스를 놓친 것과 같은 이유입니다.

해결책은 펄스를 레벨 변화로 바꾸는 것입니다. A 쪽에서 펄스가 올 때마다 신호 하나를 뒤집고(토글), B 쪽은 그 신호를 동기화한 뒤 “바뀌었는가”를 봅니다. 레벨은 다음 펄스가 올 때까지 유지되므로 B가 놓치지 않습니다. 대신 펄스 사이 간격이 B 클럭 두세 사이클보다는 길어야 합니다.

// A 쪽
always @(posedge clk_a) if (pulse_a) tgl <= ~tgl;
// B 쪽
always @(posedge clk_b) begin
  s1 <= tgl;  s2 <= s1;  s3 <= s2;   // 2단 동기화 + 이전 값
end
assign pulse_b = s2 ^ s3;           // 바뀐 순간 한 사이클 펄스

5.5클럭은 논리로 만들지 않는다

초보자가 가장 자주 하는 실수는 “일부 레지스터만 가끔 동작시키려고” 클럭을 AND 게이트로 막거나, 카운터로 클럭을 나눠 새 클럭을 만드는 것입니다.

// 나쁜 예 1: 게이트로 막은 클럭
assign gclk = clk & en;
always @(posedge gclk) q <= q + 1;

// 나쁜 예 2: 논리로 나눈 클럭
always @(posedge clk) half <= ~half;
always @(posedge half) r <= r + 1;

// 좋은 예: 클럭은 하나, 대신 enable
always @(posedge clk) if (en) q <= q + 1;

논리로 만든 클럭은 2장의 전용 클럭망을 타지 못해 skew가 커지고, 타이밍 도구가 원래 클럭과의 관계를 제대로 따지기 어렵습니다. 무엇보다 게이트로 막은 클럭은 en이 바뀌는 순간에 따라 글리치가 생겨, 레지스터가 엉뚱한 엣지에서 움직입니다. 정말 다른 주파수가 필요하면 PLL 같은 전용 클럭 회로를 쓰고, 정말 클럭을 멈춰야 하면(전력 절감) 전용 클럭 버퍼를 씁니다.

이 장의 요점
  • 클럭이 다른 신호는 2단 동기화기로 받습니다. 실패 확률은 0이 아니라 아주 작을 뿐이고 MTBF로 따집니다.
  • 여러 비트는 그레이 코드나 비동기 FIFO로, 짧은 펄스는 토글 방식으로 넘깁니다.
  • 클럭을 논리로 만들지 말고 enable을 씁니다.

책에서 이어 읽기 책은 클럭 하나로 도는 HLS 설계를 주로 다룹니다. 9장 Video Systems의 스트리밍 입출력 뒤에 이런 FIFO와 동기화기가 있다는 것을 알고 읽으면 됩니다.
