6장

HLS: C가 회로가 되는 과정

식을 직접 입력하고 목표 클럭을 정해 DFG, 스케줄링, 체이닝, 바인딩을 거쳐 FSM과 데이터패스가 만들어지는 과정을 봅니다.

6.1HLS가 하는 일

3장에서 최대공약수 C 코드를 보고 레지스터, 감산기, 컨트롤러 상태를 손으로 뽑아냈습니다. HLS(High-Level Synthesis)는 이 일을 도구가 대신 하는 것입니다. C/C++ 함수를 받아서 FSM 컨트롤러와 데이터패스로 이루어진 RTL을 만들어 줍니다.

도구 안에서는 대략 다음 순서로 일이 진행됩니다.

  1. 파싱: 코드를 연산과 데이터 의존성의 그래프(DFG, Data Flow Graph)로 바꿉니다.
  2. 스케줄링: 각 연산을 몇 번째 사이클에 할지 정합니다.
  3. 할당: 곱셈기, 덧셈기를 몇 개 만들지 정합니다.
  4. 바인딩: 각 연산을 어느 연산기에서 할지, 중간 값을 어느 레지스터에 둘지 정합니다.
  5. RTL 생성: 사이클 하나가 FSM 상태 하나가 되고, 연산기 입력 앞에는 MUX가 붙습니다.

실제 HLS 도구는 브라우저에서 돌릴 수 없으니, 이 장에서는 같은 원리로 동작하는 작은 장난감 HLS를 씁니다. 곱셈기의 지연은 3.2 ns, 덧셈/뺄셈기(ALU)는 1.1 ns, 레지스터 비용(tcq+tsu)은 0.5 ns로 둡니다. 실제 도구처럼 목표 클럭 주기를 정하면, 한 주기 안에 들어가는 연산들은 같은 사이클에 이어 붙이고(체이닝), 한 주기보다 긴 연산은 여러 사이클에 걸쳐 합니다.

목표 클럭 주기를 바꿔 보세요. 주기를 늘리면 한 사이클에 연산을 더 많이 이어 붙여 사이클 수는 줄지만, 사이클 하나가 길어져서 총 시간은 오히려 늘 수 있습니다. 주기를 줄이면 곱셈이 여러 사이클로 쪼개지고 레지스터 비용이 자주 붙습니다. 2장에서 손으로 따졌던 setup 조건을 HLS 도구가 스케줄링 단계에서 대신 따지는 것입니다. 실제 HLS 도구에서도 create_clock으로 정하는 목표 주기가 결과를 크게 바꿉니다.

“다항식 그대로”와 “호너 방식”을 비교해 보세요. 호너 방식은 곱셈이 3개뿐이라 곱셈기 하나로도 빠르지만, 모든 연산이 앞 결과를 기다리는 사슬이라 곱셈기를 아무리 늘려도 더 빨라지지 않습니다. 8개 합도 마찬가지입니다. 수학적으로 같은 식이라도 어떻게 썼느냐가 병렬성을 정합니다. HLS 도구는 정수 덧셈 정도는 알아서 재배열하기도 하지만, 부동소수점은 결과가 달라질 수 있어 함부로 바꾸지 않습니다.

6.2연산기 자체도 파이프라인된다

6.1의 장난감 HLS에서 곱셈기는 계산하는 동안 통째로 붙잡혀서, 곱셈이 3사이클이면 다음 곱셈은 3사이클 뒤에야 시작할 수 있었습니다. 실제 HLS 도구가 쓰는 연산기는 대부분 내부에 파이프라인 레지스터가 있습니다(4장). 지연이 3사이클이어도 매 사이클 새 입력을 받을 수 있는 연산기입니다. FPGA의 DSP 블록도 안에 레지스터 단이 있어서, 지연을 몇 사이클 주면 더 빠른 클럭에서 매 사이클 곱셈을 해냅니다.

그래서 실제 도구에서는 “곱셈기 하나를 여러 곱셈이 나눠 쓴다”가 훨씬 싸게 먹힙니다. 연산기의 성질을 두 숫자로 기억하세요. latency(결과가 나오기까지)와 II(다음 입력을 받기까지)입니다.

6.3FPGA 자원 지도

위 실험의 면적은 상대값이었습니다. 실제 HLS 도구는 합성 결과를 FPGA 자원 네 가지의 개수로 알려 줍니다. 이 네 가지가 무엇이고 대략 얼마나 있는지 알아야 리포트를 읽을 수 있습니다.

자원하는 일중간 크기 FPGA 한 개에
LUT6입력 논리 함수 하나. 덧셈, 비교, MUX, 작은 메모리(LUTRAM)도 여기로수십만 개
FF1비트 레지스터. 파이프라인 단과 변수를 담음LUT의 약 두 배
DSP곱셈기 + 덧셈기가 들어 있는 전용 블록. 18×27비트 정도 곱셈 한 번수천 개
BRAM포트 2개짜리 블록 메모리. 한 개에 수 KB수백~수천 개

리포트에서 DSP가 모자라면 곱셈을 줄이거나 비트 폭을 줄이고(6.5), BRAM이 모자라면 배열을 줄이거나 다시 배치하고(8장), LUT와 FF가 많으면 MUX와 파이프라인 레지스터가 많은지 의심합니다. 어느 자원이든 80%를 넘기면 배치·배선이 어려워져 클럭이 떨어지는 경우가 많습니다.

6.4if-else는 어떤 회로가 되나

6.1의 장난감 HLS는 분기 없는 식만 받았습니다. 실제 코드에는 if가 있습니다. HLS 도구가 분기를 다루는 방법은 크게 둘입니다. 양쪽을 다 계산하고 결과를 MUX로 고르거나, 조건을 먼저 보고 FSM 상태를 나누는 것입니다. 같은 코드라도 어느 쪽이 되느냐에 따라 자원과 latency가 달라집니다.

파이프라인 루프(II=1) 안의 if는 매 사이클 새 반복이 들어오므로 상태를 나눌 수 없고, 언제나 앞의 두 방법 중 하나가 됩니다. 그래서 파이프라인 루프 안의 분기는 “양쪽 다 하드웨어로 만들어진다”고 생각하는 것이 안전합니다. 7장에서 루프 안의 조건문을 밖으로 빼는 코드 재구성을 다시 봅니다.

6.5비트 폭: int를 그대로 쓰지 말 것

C의 int는 32비트이고, HLS는 그대로 32비트 하드웨어를 만듭니다. 값이 0~1000 사이라면 10비트면 충분한데도 말입니다. HLS에는 비트 수를 직접 정하는 임의 정밀도 타입이 있습니다.

#include <ap_int.h>
ap_int<12>  a, b;        // 부호 있는 12비트
ap_uint<5>  x;           // 부호 없는 5비트 (0~31)
ap_int<24>  p = a * b;   // 12비트 × 12비트 = 24비트면 넘치지 않음
ap_int<25>  y = p + c;   // 더하면 1비트 늘어남

소수점이 있는 값은 ap_fixed로 쓰며 10장에서 다룹니다. 12장의 미니 TPU가 8비트로 계산하는 이유도 여기에 있습니다.

6.6스케줄링의 여유

6.1의 리스트 스케줄링은 “남은 경로가 긴 연산부터” 배치했습니다. 이 우선순위의 바탕에는 여유(mobility)라는 개념이 있습니다. 자원이 무한할 때 가장 일찍 시작할 수 있는 사이클(ASAP)과, 전체 latency를 늘리지 않으면서 가장 늦게 시작해도 되는 사이클(ALAP)의 차이입니다. 여유가 0인 연산은 크리티컬 패스 위에 있어 미룰 수 없고, 여유가 있는 연산은 미뤄서 다른 연산과 연산기를 나눠 쓸 수 있습니다.

3장, 4장과 연결 HLS가 만든 모듈은 3장의 FSMD 그 자체이고, 바깥과는 4장의 핸드셰이크와 같은 방식(ap_start를 받고 ap_done으로 끝을 알림)으로 대화합니다. HLS를 써도 RTL을 읽을 줄 알아야 하는 이유입니다. 도구가 만든 결과를 해석하고 고칠 수 있어야 하니까요.

인자는 어떤 포트가 되나

6.7의 실험에서 배열은 메모리 포트, 반환값은 출력 포트가 되었습니다. 실제 설계에서는 함수가 CPU나 다른 회로와 어떻게 연결될지에 따라 인터페이스를 지시어로 고릅니다.

6.8HLS 설계의 검증 흐름

3장에서 RTL 테스트벤치를 썼습니다. HLS에서는 같은 일을 C 코드로 합니다. 순서는 이렇습니다.

  1. C 시뮬레이션: C 테스트벤치(main 함수)가 설계 함수를 부르고 정답과 비교합니다. 일반 프로그램처럼 몇 초면 끝나므로 알고리즘 오류는 여기서 거의 다 잡습니다.
  2. 합성: RTL을 만들고, latency, interval, 자원, 예상 클럭을 리포트로 봅니다.
  3. C/RTL co-simulation: 같은 C 테스트벤치를 그대로 써서, 이번에는 만들어진 RTL을 시뮬레이션하고 결과를 비교합니다. 실제 사이클 수도 여기서 측정됩니다.
  4. 구현: 배치·배선 뒤 타이밍을 다시 확인합니다. 합성 때의 예상 클럭은 배선 지연(2장)을 다 알지 못합니다.

C 시뮬레이션만 통과하고 co-simulation에서 틀리는 경우가 있습니다. 8장의 DEPENDENCE처럼 사실과 다른 약속을 한 지시어, 초기화하지 않은 변수, 크기를 넘는 배열 접근처럼 C에서는 우연히 맞던 코드가 대표적입니다. 그래서 co-simulation은 빼먹지 않습니다.

실제 도구에서는실제 HLS 도구는 대상 FPGA와 목표 클럭에 맞춘 연산 지연 표로 스케줄링하고, 클럭 여유분(clock uncertainty)을 빼고 계산합니다. 리포트에는 연산이 몇 번째 상태에서 실행되는지와 LUT·FF·DSP·BRAM 개수가 나옵니다. 장난감 HLS의 면적 상대값과 일대일로 대응하지는 않습니다.
이 장의 요점
  • HLS는 파싱(DFG) → 스케줄링 → 할당 → 바인딩 → RTL 생성 순으로 일합니다.
  • 목표 클럭이 체이닝과 사이클 수를 바꿉니다. 사이클 수와 총 시간은 다릅니다.
  • 파이프라인 안의 분기는 양쪽 다 하드웨어가 됩니다. 비트 폭을 줄이면 모든 자원이 줄어듭니다.
  • C 시뮬레이션 → 합성 → C/RTL co-simulation → 구현 순으로 검증합니다.
