4장

파이프라이닝

레지스터를 끼워 넣어 클럭을 올리는 대신 무엇을 내주는지 따져 보고, valid/ready로 흐름을 멈추고 이어 가는 법을 봅니다.

4.1세탁기와 건조기

빨래 한 바구니를 세탁(30분), 건조(40분), 개기(20분) 하면 90분이 걸립니다. 네 바구니를 하나씩 끝내면 360분입니다. 하지만 첫 바구니가 건조기에 들어가는 순간 두 번째 바구니를 세탁기에 넣으면, 가장 느린 건조기가 쉬지 않고 돌아가는 한 40분마다 한 바구니씩 끝납니다. 한 바구니가 걸리는 시간은 그대로인데, 시간당 처리량은 두 배 넘게 늘었습니다.

회로도 같습니다. 긴 조합 논리 중간에 레지스터를 끼워 넣으면, 각 구간(스테이지)은 짧아져서 클럭을 올릴 수 있고, 여러 데이터가 서로 다른 스테이지에서 동시에 처리됩니다.

  • latency: 데이터 하나가 들어가서 결과가 나올 때까지 걸리는 시간. 사이클 수 또는 ns.
  • throughput: 단위 시간당 나오는 결과 수. 파이프라인이 꽉 차 있으면 매 사이클 하나씩 나옵니다.

2장에서 본 것처럼 레지스터를 지날 때마다 tcq + tsu만큼의 고정 비용이 붙습니다. 그래서 무한정 잘게 쪼갤 수는 없고, 쪼갤수록 latency는 오히려 늘어납니다.

4.2파이프라인 안에서 데이터가 흐르는 모습

파이프라인에 데이터가 매 사이클 들어온다는 보장은 없습니다. 그래서 데이터와 함께 valid 비트를 같이 흘려보내서 “이 스테이지의 값이 진짜 데이터인가”를 표시합니다. valid=0인 칸을 버블이라고 부릅니다.

2단짜리 곱셈-덧셈 파이프라인을 Verilog로 쓰면 이렇습니다.

// y = a * b + c 를 2단으로
always @(posedge clk) begin
  // 1단: 곱셈
  p1 <= a * b;
  c1 <= c;          // c도 한 단 늦춰서 p1과 박자를 맞춘다
  v1 <= in_valid;
  // 2단: 덧셈
  y  <= p1 + c1;
  v2 <= v1;
end
assign out_valid = v2;
함께 가야 하는 값도 같이 늦춰야 한다 c1 <= c가 없이 y <= p1 + c라고 쓰면, p1은 한 사이클 전 입력의 곱인데 c는 지금 입력이라 서로 다른 데이터가 더해집니다. 파이프라인에서 가장 흔한 버그입니다.

4.3valid/ready 핸드셰이크

4.2의 valid는 “데이터가 있다”만 알려 줍니다. 받는 쪽이 바빠서 지금은 못 받는 경우까지 다루려면 신호가 하나 더 필요합니다. 보내는 쪽과 받는 쪽이 서로의 사정을 모를 때, 두 신호로 약속을 정합니다. 보내는 쪽은 “데이터가 준비됐다”는 valid를, 받는 쪽은 “받을 수 있다”는 ready를 올립니다. 같은 클럭 엣지에서 둘 다 1이면 전송이 일어납니다. 받는 쪽이 바빠서 ready를 내리는 것을 배압(backpressure)이라고 합니다. 3장의 start/done도 같은 생각입니다.

  • 보내는 쪽은 한번 valid를 올리면, 전송될 때까지 valid와 데이터를 바꾸면 안 됩니다.
  • valid가 ready를 기다려서 올라가면 안 됩니다. 서로 상대를 기다리다 영원히 멈출 수 있습니다.

4.4파이프라인을 멈추기: 배압

이제 파이프라인 끝에 ready를 달아 봅시다. 출력 쪽이 ready=0이면 마지막 단의 데이터를 내보낼 수 없으니, 뒤에서부터 데이터가 쌓입니다. 멈추는 방법은 크게 두 가지입니다.

  • 전체 멈춤: 마지막 단이 못 나가면 모든 단이 그 자리에서 멈춥니다. 단순하지만, 앞쪽에 빈 칸(버블)이 있어도 같이 멈춥니다.
  • 빈 칸 당기기: 각 단은 바로 뒤 단이 비어 있거나 이번 사이클에 비워지면 움직입니다. 버블을 메워 가며 더 많이 받아들이지만, “움직여도 되나”라는 정보가 뒤에서 앞으로 한 사이클 안에 전달되어야 합니다.
ready 경로도 타이밍 경로다 빈 칸 당기기에서 ready는 마지막 단에서 첫 단까지 조합 논리로 거꾸로 전달됩니다. 단이 많아지면 이 경로가 2장의 크리티컬 패스가 됩니다. 전체 멈춤도 멈춤 신호 하나가 모든 단의 레지스터로 퍼져 나가야 해서 배선이 길어집니다. 실무에서는 단 사이에 레지스터 두 개짜리 작은 버퍼(스키드 버퍼)를 넣어 ready까지 레지스터로 끊습니다.

4.5되먹임이 있으면 쪼개도 빨라지지 않는다

지금까지의 파이프라인은 데이터가 앞으로만 흘렀습니다. 그런데 누산기처럼 결과가 다시 입력으로 돌아오는 회로는 사정이 다릅니다.

always @(posedge clk)
  if (in_valid) acc <= acc + x;   // 이번 덧셈에 지난 덧셈의 결과가 필요

덧셈기가 느려서 2단 파이프라인으로 쪼갰다고 해 봅시다. 클럭은 빨라지지만, 다음 덧셈은 지난 덧셈이 2단을 다 지나야 시작할 수 있습니다. 결국 2사이클에 하나씩만 받게 되어 처리량은 그대로입니다. 되먹임 고리를 한 바퀴 도는 데 걸리는 사이클 수가 받아들이는 간격을 정하기 때문입니다. 레지스터를 옮기는 retiming으로도 고리 안의 레지스터 개수는 바꿀 수 없습니다.

해결책은 고리를 여러 개로 나누는 것입니다. 부분합 누산기를 단 수만큼 두고 입력을 번갈아 보내면, 각 누산기는 L사이클에 한 번만 더하면 되므로 전체로는 매 사이클 하나씩 받습니다. 마지막에 부분합을 한 번 더 더합니다.

7장에서 내적 루프의 II가 덧셈 지연만큼 커지는 것, 그리고 부분합 4개로 바꾸면 II=1이 되는 것이 바로 이 현상입니다. HLS 도구는 같은 일을 대신 해 주지만, 원리는 RTL과 같습니다.

4.6ready도 레지스터로 끊기: 스키드 버퍼

4.4의 끝에서 ready 경로가 길어진다고 했습니다. 단 하나짜리 버퍼를 생각해 봅시다. 버퍼가 비었거나 이번에 비워지면 받을 수 있으므로 in_ready = !full || out_ready입니다. 그러면 뒤쪽의 out_ready가 조합 논리를 거쳐 그대로 앞쪽 in_ready가 됩니다. 이런 단을 여러 개 이으면 ready가 맨 뒤에서 맨 앞까지 한 사이클 안에 달려가야 합니다.

스키드 버퍼는 레지스터를 하나 더 둡니다. in_ready를 레지스터 값(“여분 칸이 비었나”)으로만 정하므로, out_ready가 0으로 떨어진 바로 그 사이클에 앞쪽은 이미 데이터를 하나 보낸 뒤일 수 있습니다. 그 하나를 여분 칸이 받아 줍니다. 미끄러지는(skid) 차를 받아 주는 완충 구간이라는 뜻입니다.

스키드 버퍼는 처리량을 떨어뜨리지 않으면서 ready를 레지스터로 끊습니다. 대신 레지스터가 한 벌 더 들고, 꽉 찬 뒤 다시 받기 시작할 때 한 사이클이 늦습니다. 긴 파이프라인에서는 몇 단마다 이런 버퍼를 넣어 ready 경로를 짧게 유지합니다.

이 장의 요점
  • 파이프라인은 latency를 내주고 throughput을 얻습니다. 가장 느린 단이 클럭을 정합니다.
  • 함께 가야 하는 값도 같이 늦춥니다. valid로 버블을, valid/ready로 배압을 다룹니다.
  • 되먹임 고리는 쪼개도 빨라지지 않습니다. 부분합으로 고리를 여러 갈래로 나눕니다.
  • ready 경로도 타이밍 경로입니다. 스키드 버퍼로 끊습니다.
