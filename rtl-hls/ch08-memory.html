메모리와 의존성

배열이 어떤 메모리가 되는지, 한 사이클에 여러 개를 읽으려면 어떻게 쪼개야 하는지, 배열을 통한 의존성이 II를 어떻게 막는지 봅니다.

8.1배열은 어디에 저장되나

C에서 배열은 그냥 메모리지만, FPGA에는 성격이 다른 저장 공간이 세 가지 있습니다. HLS 도구는 배열 크기와 접근 방식을 보고 이 중 하나를 고르며, 지시어로 바꿀 수도 있습니다.

저장 공간크기 감각한 사이클에 접근주로 쓰는 곳
플립플롭(레지스터)칩 전체에 수십만 비트모든 원소를 동시에작은 배열, 시프트 레지스터, 완전 분할한 배열
LUTRAM (분산 RAM)LUT 하나에 수십 비트보통 쓰기 1, 읽기 1~2수십~수백 원소짜리 작은 표
BRAM (블록 RAM)하나에 수 KB, 칩에 수백~수천 개주소 2개(포트 2개)대부분의 배열

기억할 것은 하나입니다. 배열 하나가 BRAM 하나가 되면 한 사이클에 원소 두 개까지만 읽고 쓸 수 있습니다. 7장에서 UNROLL을 해도 빨라지지 않았던 이유입니다. 그래서 한 사이클에 더 많이 읽어야 할 때는 배열을 여러 메모리로 쪼갭니다(ARRAY_PARTITION). 이때 원소를 어떤 규칙으로 나누느냐가 중요합니다.

  • block: 앞에서부터 덩어리째 나눕니다. 16개를 2개로 나누면 0~7, 8~15.
  • cyclic: 카드 돌리듯 번갈아 나눕니다. 16개를 2개로 나누면 짝수 번째, 홀수 번째.
  • complete: 원소마다 따로 레지스터에 둡니다. 모든 원소를 동시에 읽을 수 있지만 크기가 크면 비쌉니다.

8.22차원 배열은 어느 방향으로 쪼개나

2차원 배열 int M[4][4]는 행 순서로 펼쳐 저장됩니다. 그래서 위 실험의 “4칸 간격”이 바로 한 열을 읽는 모양입니다. HLS에서는 몇 번째 차원을 쪼갤지 dim으로 정합니다.

int M[4][4];
#pragma HLS ARRAY_PARTITION variable=M dim=1 complete   // 행마다 따로: M[0..3][j]를 한 번에 (열 읽기)
#pragma HLS ARRAY_PARTITION variable=M dim=2 complete   // 열마다 따로: M[i][0..3]를 한 번에 (행 읽기)

규칙은 “한 사이클에 동시에 읽는 원소들이 서로 다른 메모리에 있어야 한다”입니다. 한 행을 한 번에 읽으려면 열 방향(dim=2)을 쪼개야 하고, 한 열을 한 번에 읽으려면 행 방향(dim=1)을 쪼개야 합니다. 행렬 곱처럼 한 행렬은 행으로, 다른 행렬은 열로 읽는 경우에는 두 배열을 서로 다른 방향으로 쪼갭니다.

8.3배열을 통한 의존성: 히스토그램

7장과 4장에서는 sum 같은 변수 하나를 통한 되먹임을 봤습니다. 이번에는 배열을 통한 되먹임입니다. 먼저 쉬운 경우부터 보겠습니다.

// 누적 합 (prefix sum): 매번 메모리에서 바로 앞 결과를 다시 읽는다
for (int i = 1; i < N; i++)
  out[i] = out[i-1] + in[i];

// 고친 코드: 바로 앞 결과는 레지스터 acc에 들고 있는다
int acc = 0;
for (int i = 0; i < N; i++) {
  acc = acc + in[i];
  out[i] = acc;
}

위 코드는 매 반복이 메모리 읽기를 기다려야 해서 II가 늘어나지만, 아래 코드는 되먹임이 레지스터 하나에서 끝나므로 II=1이 됩니다. 의미는 같고 코드 모양만 다릅니다.

히스토그램은 더 까다롭습니다. 어느 칸을 읽고 쓸지가 입력 값에 달려 있어서, 도구는 “이번 반복이 읽는 칸을 바로 앞 반복이 아직 쓰고 있을 수도 있다”고 가정해야 합니다.

for (int i = 0; i < N; i++) {
#pragma HLS PIPELINE II=1
  hist[in[i]] = hist[in[i]] + 1;   // 읽고(1사이클) 더하고(1사이클) 쓴다(1사이클)
}
  • 안전하게: 도구가 기본으로 하는 일입니다. 다음 반복을 3사이클 뒤에 시작해서 항상 맞지만 느립니다.
  • 직전 값 들고 있기: 진행 중인 쓰기의 주소와 값을 레지스터에 들고 있다가, 같은 칸을 읽으려 하면 메모리 대신 그 값을 씁니다(forwarding). 코드로 직접 쓰면 II=1이면서도 항상 맞습니다.
  • dependence 지시어: “연속한 입력은 같은 칸을 가리키지 않는다”고 도구에게 약속하는 것입니다. 약속이 맞으면 II=1로 빠르지만, 틀리면 결과가 조용히 틀립니다. 도구는 약속을 검사해 주지 않습니다.
#pragma HLS DEPENDENCE variable=hist type=inter false   // "반복 사이 의존성은 없다"는 약속
지시어는 약속이다 PIPELINE, UNROLL, ARRAY_PARTITION은 회로 모양만 바꾸고 결과는 바꾸지 않습니다. 반면 DEPENDENCE처럼 도구가 확인할 수 없는 사실을 알려 주는 지시어는, 사실이 아니면 틀린 회로를 만듭니다. 이런 지시어를 쓸 때는 테스트벤치에 그 약속을 확인하는 검사를 꼭 넣으세요.

8.4불규칙한 접근: 희소 행렬-벡터 곱

지금까지의 배열 접근은 a[i], a[i+8]처럼 모양을 미리 알 수 있었습니다. 대부분이 0인 희소 행렬은 0이 아닌 값만 저장합니다. 가장 흔한 형식이 CSR(Compressed Sparse Row)입니다.

  • val[]: 0이 아닌 값을 행 순서대로
  • col[]: 각 값이 몇 번째 열인지
  • rowptr[]: 행 r의 값들이 val의 어디부터 어디까지인지
for (int r = 0; r < N; r++) {
  int sum = 0;
  for (int k = rowptr[r]; k < rowptr[r+1]; k++)   // 행마다 길이가 다르다
    sum += val[k] * x[col[k]];                     // x의 어느 칸을 읽을지 실행 중에 정해진다
  y[r] = sum;
}

HLS 입장에서 어려운 점이 두 가지입니다. 안쪽 루프의 반복 횟수가 행마다 달라서(7.6) 행이 바뀔 때마다 파이프라인을 다시 채워야 하고, x[col[k]]는 주소를 미리 알 수 없어서 실험 8-1처럼 접근 모양에 맞춰 분할할 수 없습니다.

희소 행렬에서는 계산량을 아끼는 대신, 행마다 다시 채우는 비용과 불규칙한 메모리 접근이 새 병목이 됩니다. 그래서 루프를 합쳐 행 경계를 한 루프 안에서 처리하거나, 길이가 비슷한 행끼리 묶거나, 자주 읽는 x를 레지스터나 여러 복사본에 두는 식의 재구성을 합니다. 책 6장이 이 과정을 따라갑니다.

8.5정리: II를 막는 두 가지

7장과 이 장에서 본 것을 합치면, 파이프라인 루프의 II를 늘리는 원인은 결국 두 가지입니다.

  • 자원: 메모리 포트, 연산기 개수, 입출력 비트 수. 쪼개거나 늘려서 해결합니다(실험 8-1, 7장 UNROLL).
  • 재귀(되먹임): 변수나 배열을 통해 이번 반복이 앞 반복의 결과를 기다리는 경우. 레지스터로 옮기거나(누적 합), 값을 미리 넘겨주거나(forwarding), 여러 갈래로 나누거나(4장 부분합), 의존성이 없다는 사실을 알려서(dependence) 해결합니다.
실제 도구에서는아주 작은 배열은 도구가 알아서 완전 분할하기도 하고, 큰 배열은 BRAM 여러 개나 UltraRAM에 나뉘어 들어가기도 합니다. 뱅크 수 대신 한 주소의 비트 폭을 넓혀 원소 여러 개를 한 번에 읽는 ARRAY_RESHAPE도 있습니다. DEPENDENCE 지시어의 세부 문법은 버전에 따라 조금 다릅니다.
이 장의 요점
  • 배열은 기본적으로 포트 2개짜리 BRAM입니다. 한 사이클에 같이 읽는 원소는 서로 다른 뱅크에 있어야 합니다.
  • 연속 접근은 cyclic, 덩어리 접근은 block, 전부는 complete로 나눕니다. 2차원 배열은 dim으로 방향을 정합니다.
  • 배열을 통한 되먹임(히스토그램)은 forwarding이나 레지스터로 끊습니다. DEPENDENCE는 확인되지 않는 약속입니다.
  • II를 막는 것은 결국 자원과 재귀 두 가지입니다.
