9장

작업 병렬과 스트리밍

함수와 루프를 겹쳐 돌리는 DATAFLOW, ping-pong 버퍼와 스트림, line buffer로 영상을 흘려 처리하는 법을 봅니다.

9.1함수 단위로 보는 성능

7장의 IL과 II는 루프 하나 안의 이야기였습니다. 이제 한 단계 위로 올라가 함수(HLS에서는 하나의 모듈) 전체를 봅니다. 이때 쓰는 말이 둘 있습니다.

  • task latency: 함수 한 번이 시작해서 끝날 때까지 걸리는 시간.
  • task interval: 함수를 연달아 부를 때, 한 번 시작하고 다음 번을 시작하기까지의 간격. 처리율을 정하는 것은 이쪽입니다.

파이프라인이 없으면 interval = latency입니다. 함수 안의 단계들을 겹쳐 돌리면 latency는 그대로여도 interval이 줄어듭니다. 4장의 파이프라인을 연산 대신 함수나 루프 단위로 하는 셈이고, 이것을 작업 단위 파이프라인(task pipelining)이라고 합니다. 한 가지 더: 아무리 내부가 빨라도 입출력 선의 비트 수가 처리율의 상한입니다. 32비트 입력 하나짜리 함수가 100 MHz에서 매 사이클 입력을 받아도 3.2 Gbit/s를 넘을 수 없습니다.

9.2DATAFLOW: 단계를 겹쳐 돌리기

많은 처리가 “읽어 오기 → 계산 → 내보내기”처럼 여러 단계로 나뉩니다. 이 단계들을 함수(또는 루프)로 나눠 쓰고 DATAFLOW 지시어를 붙이면, HLS 도구가 단계마다 별도 회로를 만들고 단계 사이에 버퍼를 넣어 겹쳐 돌립니다.

void top(int in[N], int out[N]) {
#pragma HLS DATAFLOW
  int buf1[N], buf2[N];
  read_in(in, buf1);     // 1단계
  compute(buf1, buf2);   // 2단계
  write_out(buf2, out);  // 3단계
}

단계 사이의 배열 buf1은 메모리 두 개짜리 ping-pong 버퍼가 됩니다. 앞 단계가 다음 데이터를 한쪽에 쓰는 동안, 뒤 단계는 다른 쪽에서 이전 데이터를 읽습니다. 배열 대신 스트림(hls::stream, 하드웨어로는 FIFO)으로 이으면, 뒤 단계가 앞 단계의 첫 원소가 나오자마자 일을 시작할 수 있어 latency가 더 줄어듭니다. 스트림은 처음부터 끝까지 순서대로 한 번씩만 읽고 쓰는 경우에 씁니다.

DATAFLOW에서 interval은 가장 느린 단계가 정합니다. 4장에서 파이프라인 단을 고르게 나눠야 했던 것처럼, 여기서도 단계의 길이를 고르게 맞추는 것이 중요합니다. 가장 긴 단계 안을 7장의 루프 지시어로 더 빠르게 하거나, 단계를 둘로 나눕니다.

DATAFLOW가 안 되는 코드 한 단계가 쓴 배열을 두 단계가 함께 읽거나, 뒤 단계의 결과가 다시 앞 단계로 돌아가거나, 단계 사이에 조건에 따라 건너뛰는 호출이 있으면 도구가 DATAFLOW를 적용하지 못하거나 순서대로 실행해 버립니다. 데이터가 한 방향으로만, 생산자 하나에서 소비자 하나로 흐르게 코드를 고쳐야 합니다. 스트림 FIFO가 너무 얕으면 단계들이 서로를 기다리다 멈추는 교착(deadlock)이 생길 수도 있습니다.

9.3스트리밍 영상 처리: line buffer

FPGA가 가장 잘하는 일 중 하나는 카메라에서 들어오는 픽셀을 한 줄씩, 한 픽셀씩 흘려 처리하는 것입니다. 픽셀은 왼쪽 위부터 오른쪽으로, 줄이 끝나면 다음 줄로 한 번에 하나씩 들어옵니다(래스터 순서). 그런데 3×3 블러 같은 필터는 위아래 줄의 픽셀도 필요합니다.

프레임 전체를 메모리에 저장했다가 처리하면 메모리도 크고 지연도 깁니다. 대신 바로 위 두 줄만 저장해 두면 충분합니다. 이것이 line buffer입니다. 그리고 지금 필요한 3×3 픽셀은 레지스터 9개짜리 window에 들고 있다가, 새 픽셀이 들어올 때마다 한 칸씩 옆으로 밉니다.

for (int r = 0; r < H; r++)
  for (int c = 0; c < W; c++) {
#pragma HLS PIPELINE II=1
    pix_t p = in.read();                                  // 스트림에서 한 픽셀
    for (int i = 0; i < 3; i++) {                          // window를 왼쪽으로 한 칸
      win[i][0] = win[i][1];  win[i][1] = win[i][2];
    }
    win[0][2] = lb[1][c];  win[1][2] = lb[0][c];  win[2][2] = p;   // 새 열 채우기
    lb[1][c] = lb[0][c];   lb[0][c] = p;                         // line buffer 갱신
    if (r >= 2 && c >= 2) out.write(blur(win));                    // window가 꽉 찼으면 출력
  }

8장에서 배운 대로, win은 9개를 한 사이클에 모두 읽어야 하므로 complete 분할로 레지스터가 되고, lb는 두 줄을 서로 다른 메모리에 두도록 dim=1로 나눕니다. 그러면 사이클마다 두 줄에서 하나씩 읽고 하나씩 쓸 수 있어 II=1이 됩니다. 가장자리는 실험에서 본 것처럼 안쪽만 출력하거나, 없는 픽셀을 0이나 가장 가까운 픽셀로 채웁니다. 어느 쪽이든 그 처리 때문에 II가 깨지지 않도록 조건문을 가볍게 유지하는 것이 요령입니다.

9.4FFT: 단계마다 바뀌는 접근 모양

FFT는 N개짜리 신호를 log2N개의 단계로 처리합니다. 각 단계에서는 두 값을 짝지어 더하고 빼는 나비 연산을 N/2번 합니다. 문제는 짝을 짓는 간격이 단계마다 1, 2, 4, …로 바뀐다는 것입니다. 한 단계에 맞춰 배열을 분할하면 다음 단계에서는 같은 뱅크끼리 짝이 됩니다. 그래서 책 5장은 단계마다 따로 버퍼를 두고, 단계들을 DATAFLOW로 이어서 각 단계가 자기 모양에 맞는 메모리를 갖게 합니다.

또 하나의 특징은 입력 순서입니다. 이 방식의 FFT는 입력을 주소의 비트를 거꾸로 뒤집은 순서(비트 반전, 예: 001 → 100)로 놓고 시작합니다. 비트 반전 단계는 원소를 멀리 떨어진 자리로 옮기므로, 이것만으로도 메모리를 순서대로 읽고 쓰기가 어렵습니다.

9.5FIFO가 얕으면 멈춘다: 교착

9.2의 주의 상자에서 말한 교착을 직접 봅시다. 데이터가 두 갈래로 나뉘었다가 다시 합쳐지는 구조입니다. 위 갈래(B)는 데이터를 그대로 넘기고, 아래 갈래(C)는 이동 평균처럼 값 4개가 모여야 첫 결과를 냅니다. D는 두 갈래에서 하나씩 받아야 진행합니다.

B 갈래는 C가 첫 결과를 낼 때까지 값 4개를 들고 버텨야 합니다. 그보다 얕으면 A가 B에 쓰지 못해 멈추고, 그러면 C는 네 번째 값을 영영 못 받고, D는 C를 기다립니다. 모두가 서로를 기다리는 교착입니다. 이런 구조에서는 짧은 갈래의 FIFO를 긴 갈래가 품고 있는 값의 개수 이상으로 깊게 잡아야 합니다. C 시뮬레이션은 FIFO 크기를 무한으로 보기 때문에 이 문제를 못 찾고, C/RTL co-simulation에서야 드러나는 경우가 많습니다.

9.6더 큰 예로 이어지는 것들

이 장의 두 가지 도구, 단계를 나눠 겹쳐 돌리는 DATAFLOW와 순서대로 흘리는 스트림은 큰 설계의 뼈대가 됩니다. FFT는 9.4에서 본 것처럼 비트 반전 단계와 나비 연산 단계들을 DATAFLOW로 잇습니다. 허프만 부호화는 빈도 세기, 정렬, 트리 만들기, 부호 만들기처럼 성격이 다른 여러 단계를 잇습니다. 11장에서 볼 시스톨릭 배열도 PE들을 스트림으로 이은 DATAFLOW 설계로 쓸 수 있습니다.

실제 도구에서는DATAFLOW 조건을 어기면 도구가 경고를 내고 단계를 차례로 실행해 버리므로 경고를 꼭 확인하세요. 스트림 FIFO의 기본 깊이는 작습니다(보통 2). 단계 사이 속도가 출렁이면 STREAM 지시어로 깊이를 늘려야 하고, 교착은 C/RTL co-simulation에서 드러나는 경우가 많습니다.
이 장의 요점
  • 함수 단위 성능은 task latency와 task interval로 봅니다. 입출력 비트 수가 처리율의 상한입니다.
  • DATAFLOW로 단계를 겹치면 interval은 가장 긴 단계가 정합니다. 단계 사이는 ping-pong 버퍼나 스트림입니다.
  • 영상은 line buffer와 window로 한 픽셀씩 흘려 처리합니다. 가장자리 처리가 II를 깨지 않게 합니다.
